## 2024-05-08 - Insecure File Permissions for Telethon Sessions and Credentials
**Vulnerability:** The Telegram MCP server was creating `.env` (containing API credentials) and `.session` (containing Telegram authentication tokens) files with default umask permissions, making them world-readable (0644).
**Learning:** Default file creation on Linux/Unix systems uses the process's umask, which typically results in 0644 for files. When a library like Telethon creates a session file (SQLite database containing tokens), it does not automatically restrict file permissions. Similarly, manually writing a config file containing secrets requires explicitly restricting file permissions. This is a critical risk for CLI tools and servers that store credentials on disk.
**Prevention:** Always use `os.open` with specific secure modes (e.g., `0o600`) when creating files that will hold sensitive data. For third-party libraries that create files, explicitly `os.chmod` the files to `0600` after initialization to lock them down.
## 2024-05-09 - Information Leakage in Logs and Error Messages
**Vulnerability:** The Telegram MCP server was dumping sensitive debug logs to a world-readable `logs/` directory. Furthermore, endpoints like `get_account_info` and `list_chats` were directly returning the raw exception `str(e)` on error, which could leak stack traces or internal state to clients.
**Learning:** Returning `str(e)` in an API or CLI response often breaks the "Fail securely" principle by exposing more details than the user needs. Also, local log directories must have restricted permissions (e.g. `0o700`) to prevent local unprivileged users from reading potentially sensitive data, especially when using Telethon, which can generate verbose network logs.
**Prevention:** Catch generic exceptions and return safe, generalized error strings (e.g. "An unexpected error occurred"). Use `os.makedirs(mode=0o700)` for local log directories and set the default file log level to `INFO` rather than `DEBUG`.
## 2024-05-11 - Environment Variable Injection in CLI
**Vulnerability:** The `update_env_file` function in the CLI tool accepted unsanitized user input and directly wrote it to the `.env` file. An attacker could inject `\n` characters to add arbitrary environment variables.
**Learning:** Even simple local configuration scripts need input sanitization. Allowing raw user input to be written to structured formats like `.env` can lead to unintended execution context manipulation (e.g. overriding `PYTHONPATH`, `LD_PRELOAD`, or altering application behavior by setting unprompted env vars).
**Prevention:** Strictly sanitize input values by stripping newline (`\n`) and carriage return (`\r`) characters when programmatically modifying `.env` files.
## 2024-05-15 - Loguru F-String Injection
**Vulnerability:** The codebase was using f-strings to format log messages (e.g., `logger.error(f"Error: {e}")`). When logging user input or exception messages using Loguru with f-strings, if the substituted string contains curly braces (e.g., `{}`), Loguru will attempt to parse them as formatting tags. This can lead to a `ValueError` (Loguru F-String Injection) and crash the application, or result in malformed logs.
**Learning:** Loguru's formatting system parses tags like `<green>` and `{}` within the log string. When an f-string evaluates before being passed to Loguru, any untrusted content containing `{` or `}` will be erroneously parsed by Loguru.
**Prevention:** Always pass variables to Loguru logging methods as positional or keyword arguments using `{}` placeholders in the main log string (e.g., `logger.error("Error: {}", e)`), rather than using Python's f-strings. This ensures Loguru safely formats the data without misinterpreting the content as structural tags.
## 2023-10-27 - Path Traversal via String StartsWith
**Vulnerability:** String-based path traversal vulnerability in `validate_safe_upload_path` and `get_safe_path` (using `str(path).startswith(str(allowed_dir))`).
**Learning:** `startswith` checks on path strings can be easily bypassed. For instance, `/safe/dir-evil/file.txt` starts with `/safe/dir`, making it pass the check despite being in a different directory entirely.
**Prevention:** Always use `path.is_relative_to(allowed_dir)` (from `pathlib`) to perform a proper hierarchy-aware containment check.
## 2024-05-20 - TOCTOU Vulnerability in File Creation
**Vulnerability:** The codebase had a Time-of-Check to Time-of-Use (TOCTOU) vulnerability where a sensitive file (`.session`) was created with default loose permissions by a library, and only later secured using `os.chmod()`. During the brief window between creation and `chmod()`, another process could potentially read the sensitive contents.
**Learning:** Relying on `os.chmod()` after a file has been created leaves a race condition window. When dealing with third-party libraries that create files, if you can control the file path, you should pre-create the file securely yourself before handing it over to the library.
**Prevention:** Always pre-create sensitive files with strict permissions (e.g., `0o600`) using `os.open` with `os.O_CREAT | os.O_WRONLY` flags *before* allowing libraries to write to them. Catch specific `OSError` exceptions during file permission modifications rather than generic `Exception`.

## 2024-05-16 - File Extension Blocklist Bypass via Whitespace and Trailing Dots
**Vulnerability:** The `is_suspicious` file extension check was using simple string and path suffix operations on raw input strings. A trailing space (`evil.exe `) or trailing dot (`evil.exe.`) caused `pathlib.Path(filename).suffix` or `filename.split('.')` to yield an extension like `".exe "` or `"."`, thereby bypassing the blocklist. However, later during file saving, `sanitize_filename` or the OS would truncate or normalize those characters, allowing the malicious executable to persist.
**Learning:** Checking for malicious extensions before normalizing the input file name is a common vulnerability pattern that allows for bypass.
**Prevention:** Always validate against fully normalized strings that accurately reflect how the file will ultimately be saved or processed by the underlying OS. Strip leading/trailing whitespaces and trailing periods prior to security checks.
## 2024-05-24 - OS-Level File Normalization Bypass in Extension Validation
**Vulnerability:** The application was validating file extensions using Python's `pathlib.Path().suffix` and string matching on `.split('.')`. However, it did not account for OS-level file normalization, specifically on Windows, where trailing dots and spaces in filenames (e.g., `malware.exe ` or `malware.exe.`) are ignored by the file system. This allowed malicious files to bypass the `SUSPICIOUS_EXTENSIONS` blocklist, as the application perceived the extension as `exe ` or `exe.` rather than `exe`. Additionally, hidden files like `.bash` or `.exe` bypass `pathlib.Path().suffix` because it interprets the entire string as the stem with no suffix.
**Learning:** String-based or naive pathlib-based extension parsing is insufficient if it does not normalize the input precisely as the underlying OS would. Windows strips trailing dots and spaces before accessing the file, meaning validation logic must strip them first to analyze the *effective* file name.
**Prevention:** Always strip trailing dots and spaces (`filename.rstrip(" .")`) before extracting and validating file extensions. Furthermore, explicitly handle cases where the file name starts with a dot and has no other characters to ensure hidden malicious files are caught.
## 2024-05-24 - Information Leakage in API Endpoints Error Returns
**Vulnerability:** In `TelegramService`, methods like `download_media` and `send_message` were returning raw exception strings (`str(e)`) inside the error payloads.
**Learning:** Returning `str(e)` in an API response breaks the "Fail securely" principle by exposing more internal details or state than the user needs. This is critical in an MCP server, where these errors are fed back to an LLM context.
**Prevention:** Catch generic exceptions and return safe, generalized error strings in the data payload (e.g., "An unexpected error occurred"). Rely on `logger.exception` to log the true stack trace internally for debugging.
## 2024-05-25 - Insecure Session Management in CLI Logout
**Vulnerability:** The `logout` command in the CLI merely deleted the local `.session` file without revoking the token on the Telegram server. This left the server-side session active, creating a vulnerability if the token was ever exfiltrated.
**Learning:** For authenticated sessions tied to remote services, deleting the local file or client instance is insufficient. The session must be explicitly invalidated on the server side to ensure complete security.
**Prevention:** Always use the client library's provided logout method (e.g., `await client.log_out()`) to revoke tokens before deleting local session storage files. Fall back to manual local file deletion only if the network or API fails.
